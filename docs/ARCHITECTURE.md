# Architecture and extension boundaries

`main.py` owns startup, the per-data-folder single-instance lock, rotating diagnostics and a startup/shutdown smoke mode. `zee/gui.py` owns the desktop and stores all state on the Qt main thread. `zee/core.py` owns validation, schema v1 SQLite persistence, reporting and topology analysis. `zee/engine.py` uses up to eight QThreadPool workers and queued result signals. `zee/ping.py` calls the OS ping executable without a shell, with a deadline that includes a bounded DNS allowance. `zee/adapters.py` defines a future read-only telemetry boundary; the registry is deliberately empty.

Periodic monitoring schedules per-device intervals. Single manual batch requests are held in the GUI queue. Duplicate work per device ID is suppressed. Stops prevent new periodic probes; in-flight OS probes finish within timeout + four seconds. Queued manual batches are discarded by Stop and Close. Deletion/edit during a probe is safe: obsolete snapshots are discarded. Restarted/stale observations cannot be presented as fresh Online results. One instance per data folder avoids competing writers.

Status means observations from this computer's routing table. All-success sample percentage is called sampled availability, not contractual uptime. No-reply intervals are bounded by the observed first failure/recovery samples; unobserved time during app shutdown cannot be inferred. Time on screen uses host local time; CSV timestamps are Unix epoch seconds (UTC). Diagnoses use parent links, are probable only, and do not confirm physical faults.

SQLite database writes occur on the UI thread, avoiding unsafe cross-thread connections. SQLite WAL provides persistence and normal crash recovery. Reports currently read retained rows synchronously; very large histories/large deployments need background report queries and pagination. The current design is aimed at the initial 5–10 radios and five WAN templates. There is no schema migration beyond initial schema v1; back up before future upgrades. Database backup includes devices, settings and history. Retention removes old rows hourly and on saved settings; freed SQLite pages are reusable, but automatic full compaction is not implemented.

## Future agent protocol — design only, NOT executable support

An agent implementation would require HTTPS with verified certificates, authenticated per-agent tokens stored with OS-protected credentials, replay-resistant request IDs, versioned payload schemas, bounded batches, heartbeat expiry, local queue size/age limits, UTC clock-skew validation, and explicit device-to-agent assignments. It must not send tokens into logs, provide unauthenticated HTTP fallback or expose arbitrary shell/command execution. Recommended safe behavior when the central dashboard is unavailable: continue configured read-only local probes with bounded local buffering and backoff; do not mutate routers. The central side should merge results by agent/device/time and distinguish agent unreachable from device no reply. None of this is implemented here; there is no service installation/start/stop/uninstall procedure because no agent service exists.

## Future hardware adapters

Verify actual router model, firmware and read-only API/SNMP support before building one. An airOS adapter must verify model and available OIDs/endpoints against real hardware. Use Windows Credential Manager/DPAPI or equivalent for secrets, mask password fields, redact logs, and report unavailable metrics as unavailable. Current profile references never contain secrets. Current software sends ping only and does not reboot or configure devices.
